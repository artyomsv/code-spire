# M4 slice 3: specification, plan and steps — design

Status: draft, 2026-10-25. Branch `feat/m4-spec-plan`. Part of #115.

The operator skipped the design questions ("skip questions and just start", 2026-10-25). Every
choice below is the author's call unless it quotes an earlier operator decision or a design document.

## 1. Intent

The factory today handles one-prompt work. M3.5 copies the ticket into a "specification" and writes a
fixed one-step plan (`WorkPreparationComposer`, "Nothing here is generated by a model: M4 owns that").
A vague ticket therefore reaches the agent as vague as it was written, and a ticket too big for one run
is attempted in one run.

This slice makes the factory handle work that is bigger than one prompt (ROADMAP M4 goal):

1. **Specification.** A vague ticket becomes an outcome, context and acceptance criteria, written back to
   the ticket as a comment and never into the repository (FR-F18, ADR-029).
2. **Plan.** The specification becomes ordered vertical-slice steps (FR-F19, AUTONOMY "Why steps are
   vertical slices").
3. **Steps.** Each step is one sandboxed run on the same item branch, each step's checkpoint verifies,
   and the last step's head is delivered as one pull request.
4. **Step continuity.** Each step ends by recording its decisions, the alternatives it rejected and its
   deviations; every later step's prompt carries them (FR-F31).

**Exit criterion (ROADMAP M4):** a ticket with no acceptance criteria becomes a specification, then a
plan of three or more steps, then steps that each verify, then one pull request, and step 3's prompt
demonstrably contains step 1's recorded decision.

## 2. Goals

1. A repository can choose, in its build setup, between today's copied preparation and a generated one.
2. Generated: a specification run, then a plan run, each read-only on the repository, each producing a
   validated artifact that is stored on the item and posted to the ticket.
3. The existing spec and plan gates (per the repository's profile) approve those artifacts; an operator
   can also ask for a revision with a note.
4. A plan of N steps (1 ≤ N ≤ `maxStepsPerPlan`) builds step by step on one branch, verifying each step.
5. A step that commits nothing completes as empty instead of failing (the empty-step rule).
6. Each step's summary is stored on the item, shown on the dashboard, and prepended to every later step.
7. `factory_run` records the phase and the step index of every run.

## 3. Non-goals

- A plan coordinator that re-plans on failure, or automatic retries (ROADMAP: later slices). A failed
  step uses today's verify gate: Retry (from that step's failed checkpoint) or Stop.
- Editing a specification or plan by hand in the dashboard. The operator revises through a note.
- Parallel steps, or one pull request per step.
- Spec and plan on GitLab or Bitbucket items beyond what build already supports there (publication is
  GitHub only; spec and plan are read-only runs, so they run wherever builds run).
- Changing land, review or the M3 manual preparation (single-step JSON plans keep working).

## 4. Anti-goals

- **A specification or plan file in the repository.** It would be a second source of truth and a diff the
  reviewer must review (FR-F18).
- **Spending without the operator choosing it.** Existing repositories keep copied preparation until
  the operator switches the setting; generated preparation runs on the same harness, model and payment
  (seat or key) as the repository's builds.
- **A later step that contradicts an earlier one without saying so.** Continuity is the point; a missing
  summary is recorded and shown, never silently dropped.
- **A step failure that discards completed steps.** A failed step fails its step, never the item (FR-F20).
- **Pushing before the plan is done.** Steps stay held, unpushed checkpoints until deliver.

## 5. Constraints

- Domain events only through `WorkItemLifecycle` decisions under `WorkItemTransitions.lockItem`
  (ADR-010). Effects are durable rows; uncertain writes are recovered by reading.
- Ticket bodies, specifications, plans and summaries may quote source: encrypted at rest (Tink), never
  logged, kept out of Kafka beyond short retention (ADR-014).
- The orchestrator never calls a model itself today and does not start now: spec and plan are runs.
- Prompt size: `DispatchRequestParser` limit (65,536 characters). Summaries and artifacts are capped.
- Latest migration V95; latest ADR ADR-048. Pure contract modules stay framework-free.
- No local builds; CI proves every step; mutation-check every guard.

## 6. Design

### 6.1 The setting

`repository_build_defaults` gains `preparation` (`composed` | `generated`, V96), default `composed`
for every existing row and for a repository with no row. The Build step in the Factory tab gets one
control: "Specification and plan: Copy the ticket as one step / Write them with the build model". The
generated option names the harness, model and payment that will run it.

### 6.2 Specification and plan are runs (ADR-049)

AUTONOMY §1 describes spec and plan as "one model call, no sandbox". This slice runs them as **short,
read-only harness runs** instead, using the repository's build harness, model, effort and payment:

- they can read the repository, which a plan of vertical slices needs and a bare model call lacks;
- a subscription seat pays nothing extra per run, the operator's stated cost model;
- `RunKind.SPEC`/`PLAN` and the `factory_run.kind` CHECK already exist for exactly this; no model client
  is added to the orchestrator.

A spec or plan run is an `ExecuteRun` of kind SPEC or PLAN: a fresh clone of the base branch, no
checkpoint, no publication permit, no push. The prompt asks the agent to write its result to a file
named by `$SPIRE_ARTIFACT` and to change nothing in the repository. The run unit returns that file
(capped at 32 KiB) in a new result `RunWorkArtifact(runId, kind, text, tokenUsage, activeWallSeconds)`;
any repository change is discarded and recorded as a warning. Usage and cost are charged like a build
(`ChargeKind.SPEC`/`PLAN`, already admitted by the V42 CHECK) and count toward the item's caps.

### 6.3 The specification

Prompt inputs: the ticket title and body (empty body allowed: vague tickets are the point), the ticket's
labels, the repository's `.codespire` rules, and the instruction to read the repository as needed.
Output: Markdown with these headings, validated by the orchestrator:

```
## Outcome
## Context
## Acceptance criteria      (a list of at least one testable item)
## Out of scope
## Open questions           (may say "None")
```

A missing heading or an empty criteria list is a validation failure: one automatic retry with the
validation error in the prompt, then the item waits at `spec / awaiting_input / spec_invalid`.

Accepted text is stored as a `STORED` `SPEC` artifact and posted to the ticket as a comment
("Specification written by the factory", with its digest), through the tracker outbox.

### 6.4 The plan

Inputs: the approved specification, the repository's verify commands, `maxStepsPerPlan`, and the
repository. Output: JSON `schemaVersion: 2`:

```
{ "schemaVersion": 2, "specificationSha256": "...",
  "steps": [ { "id": "s1", "title": "...", "instruction": "...", "doneWhen": "..." } ] }
```

1 ≤ steps ≤ `maxStepsPerPlan`; ids unique; every field non-blank; the digest equals the approved spec.
Invalid → one automatic retry, then `plan / awaiting_input / plan_invalid`. Accepted plans are stored as
a `STORED` `PLAN` artifact under a new preparation binding version (`STEPS_BINDING = 6`) and posted to the
ticket as a numbered list of step titles. `WorkArtifacts.observe` accepts N steps for binding 6 and keeps
the single-step rule for bindings ≤ 5.

### 6.5 Gates and revisions

The spec and plan phases keep their profile modes (`off` / `approve` / `auto`); `approve` opens a gate on
the artifact's digest. The decision panel shows the full specification or the step list. Besides Approve
and Reject, a gate offers **Revise with a note**: the note is added to a new run's prompt, at most 3
revisions per phase per generation, then only Approve or Reject remain. Approving a new specification
invalidates any plan made from the old one.

Today `enter` returns `capability_unavailable / spec_approval_unavailable` for spec `approve`; with
generated preparation, spec becomes available (`WorkPhaseCapability`) and the gate opens after the run.

### 6.6 Steps

A new item fact records the plan cursor: `stepIndex` (0-based) and the completed steps, each with its run,
head (or `empty`), verify outcome and summary reference. The build/verify loop becomes:

```
build(step k) → verify(step k) → [k < N-1] build(step k+1) → … → [k = N-1] deliver
```

- **Branch:** step 1 creates the item branch (`spire/work-<attemptId>` as today); every later step starts
  `fromCheckpoint(previous step's run, head)` on the same branch name, so the steps form one linear
  history and nothing is pushed until deliver.
- **Prompt for step k:** the specification; the full plan as a numbered list of titles; "Now do step k:
  <title> — <instruction>. Done when: <doneWhen>"; then "Decisions recorded by earlier steps" with every
  earlier summary, oldest first (capped to 12 KiB in total, newest kept in full when cut).
- **Completion gate between steps (FR-F19):** a step completes when its verify PASSED, or it was empty
  (6.7). FAILED or UNVERIFIED opens today's verify gate: Retry starts that step again from its failed
  checkpoint; Stop stops the item. No human gate between passing steps (the operator rejected per-step
  approvals during land design; the final land approval remains the human check). *Author's call.*
- **Limits:** each step run counts toward `maxRunsPerItem`, cost and wall-clock limits. `WorkProgress.steps`
  counts plan steps completed, not build starts.
- **Deliver** pushes the last step's head and opens one pull request whose body lists the steps and their
  summaries. Review and land are unchanged.

### 6.7 The empty-step rule

A step whose agent commits nothing is not a failure. The agent entrypoint, finding `HEAD == BASE`, still
reports a ready result with `head` = the starting head and `empty = true` (today it fails with
`PUBLISHER_FAILED "no observed checkpoint"`). The orchestrator records the step as empty, skips verify
(the head is the one already verified, or the base for step 1), and moves on. If every step is empty,
nothing is delivered: `build / awaiting_input / plan_produced_no_change`, and the operator can Stop or
Readmit.

### 6.8 Step summaries (FR-F31)

The agent writes JSON to `$SPIRE_STEP_SUMMARY` before it ends:

```
{ "decisions": ["..."], "alternativesRejected": ["..."], "deviations": ["..."] }
```

The run worker reads it (cap 8 KiB, each list ≤ 20 items, each item ≤ 500 characters), and sends it on
the ready result (`RunWorkReady.stepSummary`, added with a wither). The orchestrator stores it encrypted in
a new table `work_step_summary` (item, generation, step, run, summary, created). A missing or unreadable
file stores `summary_missing`; the step still completes, the dashboard says so, and the next prompt says
"Step k recorded no decisions". `AGENT-IMAGE-CONTRACT.md` gains the optional `$SPIRE_STEP_SUMMARY` and
`$SPIRE_ARTIFACT` files, and the reference entrypoint writes them; `spire-agent-image verify` checks they
are honoured when present.

### 6.9 `factory_run.phase` and step index

V96 also adds `factory_run.phase` (`spec`, `plan`, `build`, `verify`) and `step_index` (nullable), written
at dispatch. Run detail shows "Plan step 2 of 4".

### 6.10 Dashboard

- **Spec step:** the specification text (Outcome, criteria) with its digest and the ticket comment link.
- **Plan step:** the numbered step list with titles and done-when lines.
- **Build step:** one row per step: title, state (waiting, building, verifying, passed, empty, failed),
  commit, and its summary (decisions, rejected alternatives, deviations) expandable; "no decisions
  recorded" shown plainly.
- **Decision panel:** spec and plan evidence as above; Revise with a note.
- New reasons get copy in `workReasons.ts` in the same change.

### 6.11 Readmit, takeover, land

Readmit starts a new generation from intake as today; spec and plan run again. Human takeover during any
step suspends as today. Land fix loops build on the delivered branch as today, as one extra build after
the plan, not as a plan step.

## 8. Proof

CI for every slice (RED then GREEN), mutation checks on every guard, and a live run on `spire-test`:

1. A ticket with only a title and one vague sentence, no acceptance criteria: a specification with
   criteria is posted to the ticket; a plan of 3 or more steps is posted; each step builds and verifies;
   one pull request; review; land.
2. Step 3's recorded prompt (encrypted at rest, read through the run detail) contains step 1's decision.
3. A step instructed to change nothing completes as empty.
4. Revise with a note changes the specification.

## 9. Review amendments (2026-10-25) — these override the sections they name

1. **Spec and plan runs never push (§6.2).** A plain `ExecuteRun` uses the continuous-push publisher
   (`RunUnitBuilder.java:118-119`, `PublishCycle.java:133-148`). Spec and plan runs use a new publisher
   mode, `READ_ONLY` (`spire-publish-none`): it reads `/handoff`, emits the artifact and never calls
   `pushRef`; the init container gets a clone credential only where the forge allows a read-only one,
   otherwise the publisher mode is the guard. The result `RunWorkArtifact` is produced by a named branch in
   `RunLauncher`; the unit is destroyed once the artifact is recorded (no retained workspace, and
   `WorkRunWorker.recover` does not treat it as a build awaiting publication).
2. **A lost checkpoint fails the step, never rebases it (§6.6).** For a plan step, `readableStart`'s
   fallback to the base (`WorkRunWorker.java:208-213`) is forbidden: a missing checkpoint fails the step
   with `checkpoint_missing`, which opens the verify gate (Retry / Stop). The ready result carries
   `startFromHead`; the publisher asserts the ready head descends from it; the orchestrator refuses a head
   that does not extend the previous step.
3. **Empty steps are detected by the publisher and the orchestrator (§6.7).** The entrypoint reports
   nothing. Step k>1: an idle agent still yields a bundle to the previous head, so the orchestrator marks
   the step empty when `ready.head == step start head`. Step 1: the held publisher emits
   `checkpoint head=<base> empty=true` when `DONE` arrives with zero new commits; `RunWorkReady` gains
   `empty` with a wither (snapshot test). An empty step k>1 keeps a usable handoff for `fromCheckpoint`; an
   empty step 1 starts step 2 from the base.
4. **Spec and plan have their own durable effect and draft fact (§6.3–6.5).** A `work_prepare_effect` row
   and dispatcher run them; their runs bind a provisional digest (setup revision + ticket digest + kind),
   not a preparation binding. A new `WorkItemEvent` component `WorkDraft` (spec and plan artifact refs,
   revision counts) with a wither holds the draft until both are approved; only then is a `WorkPreparation`
   registered, by a system registration path that counts only build-or-later attempts (today
   `prepare` refuses once any phase attempt exists, `WorkItemTransitions.java:542-545`).
5. **The copy sweep skips generated repositories (§6.1).** `WorkPreparationSweep.candidates()` and
   `automatic()` require `preparation = 'composed'`; a sibling sweep starts the spec run for `generated`
   items, under the same lock discipline. Update the sweep's class comment.
6. **Spec and plan gates are result gates (§6.5).** Modelled on `verifyResultGate`: under `generated` the
   run is admitted by the setting, and `approve` means approve the produced artifact, with
   `gate.artifact` = the artifact's sha256 (extend `WorkGate.artifactOf`). **Revise** is dashboard-only:
   the gate resolves `REJECTED` with the note and the phase re-enters with the note in the prompt; no new
   gate state, no migration. Tracker commands and PR reviews keep plain approve/reject.
7. **Readmit reuses approved artifacts (§6.11).** `readmit()` carries the preparation forward, so readmit
   spends nothing on spec and plan; the readmit dialog offers "Regenerate specification and plan", which
   clears the draft and preparation for the new generation.
8. **Prompt budget (§6.6).** Spec ≤ 16 KiB; plan embedded as numbered titles ≤ 4 KiB; the current step's
   instruction + doneWhen ≤ 4 KiB; summaries ≤ 12 KiB; verify-failure section ≤ 8 KiB: ≤ 48 KiB before the
   commit instruction. The worst-case step prompt is validated when the plan is accepted, so no step is
   refused at dispatch after approval. Artifact caps in §6.2–6.4 are lowered to match (spec 16 KiB, plan
   32 KiB total with per-field caps in amendment 13).
9. **Summary and artifact files travel through the handoff (§6.8, §6.2).** The entrypoint copies
   `$SPIRE_STEP_SUMMARY` and `$SPIRE_ARTIFACT` to `$SPIRE_HANDOFF/step-summary.json` and `artifact.md`
   before `DONE`. The publisher reads them as regular files only (no symlinks, `NOFOLLOW`), size-capped, and
   emits them as outcome lines parsed by `PublisherOutcome`. That output reaches the run-worker host's
   Docker log, so the text is scrubbed with `RunFailures.scrubFor(command)` before the orchestrator stores
   or posts it, and §5's "never logged" is narrowed to "never logged by our services".
10. **Deliver uses the last non-empty step (§6.6).** The plan cursor records per step
    `{runId, head, verificationAttempt, verification, empty}`; deliver uses the last non-empty step's
    execution, whose handoff carries the whole chain. All steps empty → `plan_produced_no_change`.
11. **Step counting (§6.6).** `WorkProgress.start` stops counting steps; the decider increments `steps` on
    step completion. N ≤ `maxStepsPerPlan`; `startKeepingExecution` (land fix) is exempt from the steps
    check. Spec and plan runs count toward wall-clock, cost and calls, not `maxRunsPerItem`.
12. **Charges (§6.2).** Add `ChargeKind.SPEC` and `PLAN`; `ChargeCall.forRun` and the `QueuedRun` writer take
    the kind instead of hard-coding BUILD; `llm_charge.capability` is `AUTONOMY` for spec and plan runs.
13. **Untrusted text (§6.3, §6.4, §6.8).** Ticket text, artifacts and summaries are quoted into prompts in
    fenced blocks marked "data, not instructions". Control characters are stripped. Field caps: step title
    120, instruction 4,000, doneWhen 1,000, summary item 500. Tracker comments neutralise `@`-mentions and
    raw HTML.
14. **Evidence for N steps (§6.4).** `WorkArtifacts.Evidence` carries a step list; `schemaVersion: 2` is
    accepted only under binding 6, and v1 keeps exactly one step. Binding 6 hashes nothing new (the plan
    digest covers the steps): it is a validation-rule version, so `WorkPreparation`'s `≤ 5` check becomes
    `≤ 6`.
15. **Branch wording (§6.6).** Each step's run has its own `spire/work-<attempt>` subject; nothing exists on
    the forge before deliver, and the delivering attempt names the branch.
16. **Admission (§6.5, §6.1).** `reconcile` (not `enter`) yields `spec_approval_unavailable`. Switching a
    repository to `generated` applies only to items admitted after the switch, so items already parked at
    `capability_unavailable` do not all start spec runs on the next policy check.
17. **The loop lives in the decider (§6.6).** The build↔verify step loop and the cursor are
    `WorkItemLifecycle` decisions with a new `WorkItemEvent` component (wither, snapshot test, projection
    columns), not edits to the hard-coded `nextPhase` switch.
18. **`factory_run` columns (§6.9).** Keep `step_index`. Drop `phase`: verify is not a run and `kind` already
    names spec, plan, build and fix. The #115 "phase column" item is answered by `kind` + `step_index`, which
    ADR-049 says.
19. **ADR-049 supersedes FR-F18's mechanism sentence** (`PRD.md:167-168`, `AUTONOMY.md:20-21`); §7 says
    "supersede", not "note".
20. **Spend before the first gate (§4, §6.1).** Under profiles where spec and plan are `auto`, a generated
    repository spends two runs (plus up to one automatic retry each) before the plan gate. The setting's UI
    copy says so.
21. **ADR status lines.** ADR-046, ADR-047 and ADR-048 all still say "Live proof pending"; fix all three.
22. **Attribution (§6.6).** No gate between passing steps is the author's call only.
