# Software Factory — The Execution Layer

Which agent harness runs, under whose credential, inside which image, on which runtime. This is the
part of the design most constrained by things outside the codebase — vendor terms, software licences
and enterprise policy — so it is written as findings first and decisions second.

---

## 1. Two legal surfaces, not one

Confusing these is the single easiest mistake in this area.

| | **Harness software licence**<br>*may we run and ship this program?* | **Model provider terms**<br>*may this credential run unattended?* |
|---|---|---|
| **Codex CLI** | Apache-2.0 | OpenAI's — it is OpenAI's client for OpenAI's service |
| **Claude Code** | **none published** | Anthropic's — same reason |
| **pi** | MIT | **none of its own** |
| **opencode** | MIT | **none of its own** |
| **OpenHands** | MIT | **none of its own** |
| **Gemini CLI** | Apache-2.0 | Google's |
| **Goose** | Apache-2.0 | **none of its own** |

`pi`, `opencode`, `OpenHands` and `Goose` are empty harnesses pointed at somebody else's model API.
They have no service behind them, so there are no "pi terms" — the terms that apply are whichever
provider credential is put into them. Codex CLI and Claude Code carry both surfaces because each is
a vendor's own client for that vendor's own service.

## 2. Vendor terms, quoted (retrieved 2026-09-01)

Terms for automated use **changed twice during 2026**. Every finding below carries its retrieval
date and must be re-checked before the corresponding arm ships.

### Anthropic — Consumer Terms of Service, effective 2025-10-08

Listed among prohibited uses, §3:

> "Except when you are accessing our Services via an Anthropic API Key or where we otherwise
> explicitly permit it, to access the Services through automated or non-human means, whether through
> a bot, script, or otherwise."

§2 adds: *"You may not share your Account login information, Anthropic API key, or Account
credentials with anyone else or make your Account available to anyone else."*

**Reading:** a Pro/Max subscription may not drive an agent unattended. The API-key carve-out is
written into the ban itself. This is also enforced server-side: since January 2026 subscription OAuth
tokens used outside first-party Claude Code are rejected.

### Anthropic — Commercial Terms of Service, effective 2025-06-17

§A.1:

> "Subject to these Terms, Anthropic gives Customer permission to use the Services, including to
> power products and services Customer makes available to its own customers and end users."

§D.4 (Use Restrictions):

> "Customer may not and must not attempt to (a) access the Services to build a competing product or
> service, including to train competing AI models or **resell the Services** except as expressly
> approved by Anthropic…"

§D.5: *"Customer is responsible for all activity under its account."*

**Reading:** no automation prohibition at all, and explicit permission to power products for one's
own end users. §D.4's resale clause is the reason bring-your-own-key is a **licence requirement**,
not merely a cost preference — see ADR-030.

### OpenAI — Services Agreement, effective 2026-01-01

§3.1 forbids sharing or reselling account access. §3.3 restricts unlawful use, third-party rights
violations, reverse engineering and using Output to develop competing models. **There is no
automation clause.** The consumer Terms of Use prohibit only *"Automatically or programmatically
extracting data or Output"* — scraping, not agentic use.

### OpenAI — Codex documentation

> "Use API key authentication for programmatic Codex CLI workflows, such as CI/CD jobs."

`printenv OPENAI_API_KEY | codex login --with-api-key`; enterprise workspace automation uses
`CODEX_ACCESS_TOKEN` with `codex login --with-access-token`. Unattended invocation is
`codex exec --sandbox workspace-write --ask-for-approval never`; the read-only CI shape is
`--sandbox read-only --ask-for-approval never`. **Network access is off by default** in
`workspace-write`.

### OpenAI — Service Terms

> "Output generated by code generation features of our Services, including OpenAI Codex, may be
> subject to third party licenses, including, without limitation, open source licenses."

**Reading:** a factory merges generated code at volume. Licence provenance is therefore a real
pipeline concern, not a footnote — NFR-F10.

### Where the record is thin

No OpenAI document was found that **affirmatively permits** using a ChatGPT subscription for
unattended automation. It is not prohibited in writing, and OpenAI's own documentation steers to API
keys. The deployment decision to use subscription auth for Codex is the operator's, recorded in
[`../DECISIONS.md`](../DECISIONS.md) with its own provenance. The design supports it; the design does
not assert that it is sanctioned.

## 3. Credentials

### 3.1 The pool

A single credential is not enough: a subscription has windowed quota, and an API key has rate limits.
The unit is a **pool** with per-member state — the same shape as the existing per-host circuit
breaker, keyed by credential instead of host.

```
available ──429 / window exhausted──► rate_limited(until) ──expiry──► available
          ──401───────────────────► rejected      (operator action required)
          ──operator────────────────► disabled
```

Four rules:

1. **Rotation is not a new call.** A rotated retry is the *same* logical call and must reuse its
   charge identity. The ledger already had to distinguish a re-run (new identity) from an auto-retry
   (shared identity); rotation is the second kind. Getting it wrong inflates every run.
2. **Exhaustion is a fact, not a failure.** `ALL_CREDENTIALS_EXHAUSTED` is a first-class refusal with
   its own status and an attention row naming **when capacity returns** — the same shape as
   `CAP_REACHED`. Not a crash, not a retry storm.
3. **Least-recently-exhausted, never round-robin.** Round-robin spreads load thinly across every
   member and burns all windows together, so capacity goes from full to zero with no warning.
4. **Token expiry is distinguishable from quota exhaustion.** They look alike at the HTTP layer and
   need opposite operator action.

### 3.2 What subscription auth breaks, and why that was foreseen

A subscription does not bill per token, so a subscription-authenticated run has **no price**. ADR-025
wrote this scenario down in advance:

> *"a money-denominated cap will be inert by design on an `UNMETERED` deployment, so the eventual cap
> needs a token- or call-count axis regardless of pricing mode"*

Consequences:

- Such a run charges `pricing_mode = UNMETERED` — an **asserted** zero, never a coerced one.
- `SpendGate`'s call-count axis becomes the live money control.
- A third axis joins the gate: **quota headroom**. "May this run start?" becomes "is there a
  credential with room?"

Arms that use the existing LLM provider registry — `pi`, `opencode` — remain fully **metered**, so an
operator can mix an unmetered bulk harness with a metered one where cost attribution matters.

### 3.3 Injection

Credentials are injected into the sandbox at start, as a file or environment variable, and:

- never written into an image layer,
- never present in a `docker inspect`-visible field where avoidable,
- redacted from every event, artefact and transcript before it leaves the worker,
- scoped to the single run, and revoked or rotated on the pool's schedule, not the run's.

Codex subscription auth is an `auth.json` blob obtained once by an interactive login. The operator
performs that login; Code Spire stores the result in the **existing** encrypted registry (Tink
AES-256-GCM with AAD binding) and injects a copy per run. It expires, so the pool needs a refresh
path.

## 4. Agent images

### 4.1 The image is a contract, not a base

An enterprise on an approved golden base image cannot write `FROM spire-agent-codex`. So the shipped
images are **reference implementations of a published contract**, and any image may satisfy it.

| The image must | Why |
|---|---|
| have the harness binary on `PATH` under its declared name | the adapter builds argv |
| declare and run as a **non-root** UID | the sandbox boundary is real |
| contain `git` and a POSIX shell | branch, commit, push, run the repository's checks |
| honour `SPIRE_WORKSPACE` as the writable working directory | one path the runtime mounts |
| write the run event stream to the declared descriptor | events reach the store |
| honour `HTTPS_PROXY` / `NO_PROXY` and the CA-bundle variables | TLS interception is normal in these shops |
| exit non-zero on failure, and only then | the outcome is an exit code |
| contain no credential | credentials are injected |

**`spire agent-image verify <ref>`** boots any image and passes or fails it against that contract.
This follows the house rule that a seam is not done until a gate enforces it, and matches how the
comparable wire protocols in this space prove an implementation — with a conformance suite, not a
grep.

### 4.2 Shipped images

```
spire-agent-base            git, CA certs, non-root user, workspace layout, run entrypoint
  ├─ spire-agent-codex      + Codex CLI      (Apache-2.0)
  ├─ spire-agent-pi         + pi             (MIT)
  ├─ spire-agent-opencode   + opencode       (MIT)
  └─ spire-agent-claude     + Claude Code    (installed at build, never redistributed)
```

One base with thin layers, not four independent images: four images means four places to patch a CVE
and four entrypoints that drift. This repository already carries three separate tech-debt entries
that are literally *"duplicated with no drift guard"*.

All images are digest-pinnable, signed, and published with an SBOM — because an enterprise mirrors
them into their own registry and runs them through an approval process before anything else can
happen.

### 4.3 The second dimension: the repository's toolchain

An agent that cannot run the repository's tests has no back-pressure, and back-pressure is what keeps
an autonomous run from drifting. So the sandbox needs the **project's** toolchain too — a JDK and
Gradle for one repository, a Python environment for another. No base image can carry every stack.

Resolution, and the guard:

```
per-run override  >  per-repository setting  >  harness default  >  built-in
```

The per-repository level selects from an **operator-defined allowlist**, never free text (ADR-035).
A repository-chosen image decides where the operator's credentials are injected; free text there
means anyone who can open a pull request can name an image and receive the model key, the git token
and the CA bundle on startup.

### 4.4 Sidecar injection — named and deferred

The alternative is injecting the harness into the customer's own image at run time via an init
container copying into a shared volume, the way major CI runners ship themselves. The customer image
would then carry only their toolchain and never rebuild when a harness updates.

It is the better end state and it is real work: Codex is a single Rust binary and injects cleanly,
but `pi`, `opencode` and Claude Code are Node-based and would need a bundled runtime shipped
alongside. **Deferred until repeated friction pays for it.** The image contract makes deferring safe,
because a customer who needs it today can build an image that passes the suite.

## 5. Runtime arms

| Arm | Isolation | Notes |
|---|---|---|
| **`docker`** (M0) | sibling container over the Docker socket | socket access is root-equivalent on the host — stated in `SECURITY.md`, narrowed by rootless Docker or Podman |
| **`kubernetes`** (M5) | one Pod per run | no socket, real `NetworkPolicy`, real limits, TTL cleanup; lands into the Helm/kustomize artefacts that already exist |

Egress is deny-by-default with an allowlist for the model endpoint, the git host and the package
registries the repository needs. Codex helps here: `workspace-write` already has network off unless
enabled.

## 6. Implementation order and why

1. **Codex** — Apache-2.0, non-interactive subcommand with NDJSON and honest exit codes, OS-level
   sandbox modes built in, network off by default, and OpenAI's own documented automation path.
2. **pi** — MIT, provider-agnostic through the existing registry, and the only arm with a
   bidirectional session mode, which is what makes **steer** implementable. Building it is what turns
   the seam from an assertion into a fact.
3. **opencode** — MIT, shaped like `pi`; its weaker default output stream may push it to `opencode
   serve`.
4. **Claude Code** — API key only, installed rather than shipped.

Others — Gemini CLI, OpenHands, Goose, Cline, Qwen Code — are recognised as viable arms and are not
scheduled. Each is an adapter plus a registry entry, which is exactly the cost the seam exists to
make small.
