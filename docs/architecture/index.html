Spired architecture

A set of drawings of the system: each deployable part on its own sheet, then the parts together.

Module names keep the spire- prefix. Every sheet was drawn from the code, not from the older documents. Checked against the code at 0e6fbde3, 2026-11-15.

  1. 01spire-gatewayThe front door. It checks each webhook and puts it on the bus.
  2. 02spire-orchestratorThe core. It decides what happens next, and it is the only writer of domain events.
  3. 03spire-review-workerThe hands of the reviewer. It does every step that touches the outside world.
  4. 04spire-run-workerIt turns one run command into containers on a Docker host, and reads what they say.
  5. 05The run unitFive small images work together for one run. Each one holds only what it needs.
  6. 06spire-publisherThe only container in a run that can write to the forge. It checks before it pushes.
  7. 07spire-model-proxyIt keeps the model credential away from the agent.
  8. 08spire-egress-proxyThe one way out of a run unit. It records every host, and it can refuse.
  9. 09spire-agent-codex, spire-agent-claude-codeThe agent images. Each one runs a coding CLI in a box with no way to push.
  10. 10spire-uiTwo things in one image: the dashboard, and the nginx that is the only way in.
  11. 11The librariesWhich module is built from which. A dot means a direct dependency in the Gradle build.
  12. 12The message busEvery Kafka topic, who writes it and who reads it.
  13. 13How a review travelsOne pull request event, from the webhook to the comment on the forge.
  14. 14How a work item is builtThe factory: from a labelled ticket to a merged pull request.
  15. 15The whole systemFour services around one message bus, one way in, and a disposable box for each agent run.
