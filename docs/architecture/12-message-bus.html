The message bus

Every Kafka topic, who writes it and who reads it.

The services do not call each other. One service writes a message to a topic, and another one reads it. There are 21 topics. All names start with cs..

The rules of the bus

  • A message is the only way for one service to tell another one something. The one synchronous edge is the webhook: the gateway answers the forge with 202.
  • Only the orchestrator writes domain events (cs.events). The workers write results, and a saga in the orchestrator turns a result into an event.
  • All messages of one review have the same key, so they stay in order. Runs are keyed by run id.
  • A diff is never put on the bus. A finding is: it travels inside the event.
  • The bus is not encrypted by the application. It relies on short retention and on disk encryption of the broker.

How each consumer reads

TopicDetail
cs.commandsOne record at a time. A command can take minutes: two LLM calls and a posting backoff.
cs.review-runsA separate lane with its own pool, so a review never waits behind a build. It starts at the oldest record.
cs.run-commandsIn order. It starts at the newest record. The record is acked when the claim is written, not when the run ends.
cs.run-controlEach run worker replica has its own consumer group. Every replica gets every record, and the one that owns the run acts.
cs.run-eventsBest effort. The writer does not wait for the broker, and a failed read is ignored.
cs.eventsTwo groups in the orchestrator: the projector reads from the start, and the supersede listener reads from now.

Dead letters

A record that fails in the orchestrator, the review worker or the run worker goes to cs.dlq. The orchestrator stores it, shows it in the dashboard, and can replay it to its first topic.

Two channels in the orchestrator use cs.work-dlq instead. Nothing reads that topic, and the dashboard does not show it.

Coupling to watch

  • cs.repository-integration has two writers (the gateway, and the orchestrator for a manual registration) and two reader groups in the orchestrator.
  • Four topics have one side missing. cs.integration is read but never written. cs.work-events, cs.repository-activity and cs.work-dlq are written but never read.
  • README.md and docs/factory/ARCHITECTURE.md still say that the gateway publishes to cs.integration. The code publishes to cs.repository-integration.
  • There is one path that goes around the bus: the orchestrator deletes rows in the database schema of the review worker (sheet 02).
  • The message types are in spire-contract. A new field in a nested type is not seen by the contract snapshot test.
